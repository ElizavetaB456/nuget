# depviz — визуализация графа зависимостей NuGet

Практическая работа № 2 по дисциплине «Конфигурационное управление»,
вариант 3.

## Общее описание

`depviz` — CLI-приложение для анализа и визуализации графа зависимостей
пакетов .NET (NuGet). Зависимости получаются напрямую через NuGet API v3
(HTTP + разбор XML/JSON), без менеджеров пакетов и сторонних библиотек.
Реализация — Python 3.10+, только стандартная библиотека.

Возможности:

* получение прямых зависимостей пакета заданной версии из репозитория NuGet;
* построение транзитивного графа обходом в ширину (BFS без рекурсии)
  с ограничением глубины и фильтрацией пакетов по подстроке;
* обнаружение циклических зависимостей;
* тестовый режим — граф из текстового файла;
* порядок загрузки зависимостей;
* описание графа на языке PlantUML и вывод изображения.

## Структура репозитория

```
src/depviz/
  __main__.py   точка входа (python -m depviz)
  app.py        сценарий работы и вывод результатов
  cli.py        опции командной строки и их проверка
  versions.py   версии и диапазоны версий NuGet
  nuget.py      работа с NuGet API v3, разбор .nuspec
  testrepo.py   тестовый репозиторий из файла
  graph.py      построение графа (BFS), поиск циклов
  order.py      порядок загрузки (топологическая сортировка)
  plantuml.py   генерация PlantUML и получение изображения
tests/          модульные тесты (unittest), поддельный сервер NuGet
examples/       тестовые репозитории
run.sh          запуск приложения и тестов
```

## Параметры

| Опция | Описание |
|---|---|
| `-p`, `--package` | имя анализируемого пакета (обязательно) |
| `-r`, `--repo` | URL репозитория NuGet или путь к файлу тестового репозитория (обязательно) |
| `-t`, `--test-mode` | режим работы с тестовым репозиторием |
| `-v`, `--version` | версия пакета (обязательна вне тестового режима) |
| `-d`, `--max-depth` | максимальная глубина анализа (целое ≥ 1, по умолчанию 3) |
| `-f`, `--filter` | подстрока: пакеты с ней в имени не анализируются |
| `-l`, `--load-order` | вывести порядок загрузки зависимостей |
| `-u`, `--uml` | вывести граф на языке PlantUML и показать изображение |
| `-o`, `--output` | файл `.puml` (по умолчанию `out/<пакет>.puml`), только с `-u` |
| `--no-show` | не открывать изображение (только вывести путь/URL) |

Проверки параметров: формат имени пакета (в тестовом режиме — только
большие латинские буквы), схема `http/https` у URL, существование файла
тестового репозитория, наличие и формат версии, целое положительное
значение глубины, фильтр без пробелов по краям и не исключающий сам
анализируемый пакет, расширение `.puml` у `--output`.

Коды завершения: `0` — успех, `1` — ошибка репозитория (сеть, нет пакета
или версии, ошибка формата файла), `2` — ошибка параметров.

## Сборка и тесты

Сборка не требуется, зависимостей нет.

```sh
./run.sh --help        # справка
./run.sh test          # все тесты (python -m unittest)
```

Без `run.sh`: `PYTHONPATH=src python3 -m depviz ...`.
Тесты не обращаются к сети: ответы NuGet имитируются (`tests/fake_nuget.py`).

## Этап 1. Параметры

На этапе 1 приложение выводило все параметры в формате `ключ=значение`:

```
$ ./run.sh -p Serilog -r https://api.nuget.org/v3/index.json -v 4.0.0 -d 2 -f Test
package=Serilog
repo=https://api.nuget.org/v3/index.json
test_mode=False
version=4.0.0
max_depth=2
filter=Test

$ ./run.sh -p Serilog -r https://x -v 1 -d 0
Ошибка параметров: argument -d/--max-depth: значение должно быть не меньше 1, получено 0
$ ./run.sh -p A -r nofile -t
Ошибка параметров: файл тестового репозитория не найден: 'nofile'
```

## Этап 2. Получение зависимостей NuGet

1. Если `--repo` оканчивается на `.json`, это индекс сервиса
   (`https://api.nuget.org/v3/index.json`); из него берётся адрес ресурса
   `PackageBaseAddress/3.0.0`. Иначе `--repo` считается этим адресом
   (`https://api.nuget.org/v3-flatcontainer/`).
2. `{base}/{id}/index.json` — список версий; заданная версия проверяется
   на существование (с нормализацией: `1.0` → `1.0.0`).
3. `{base}/{id}/{версия}/{id}.nuspec` — манифест пакета; из элементов
   `<dependency>` извлекаются id и диапазон версий. Если зависимости
   разбиты на группы по целевым платформам, берётся их объединение.
4. Диапазон (`1.0`, `[1.0,2.0)`, `(,1.0]`, `[1.0]`) разрешается в
   минимальную подходящую опубликованную версию — как в NuGet
   (*lowest applicable version*); предрелизы — только если нижняя граница
   сама предрелиз.

На этапе 2 выводились прямые зависимости в виде
`<зависимость> <диапазон> -> <выбранная версия>`.

## Этап 3. Граф зависимостей

* BFS без рекурсии (очередь `deque`). Глубина корня — 0; пакеты на
  глубине `--max-depth` попадают в граф, но не раскрываются.
* Пакеты, имя которых содержит `--filter` (без учёта регистра),
  исключаются вместе с поддеревьями.
* Каждый пакет раскрывается один раз, поэтому циклы не приводят к
  зацикливанию; найденные циклы выводятся.
* Тестовый режим (`-t`): файл, где пакеты названы большими латинскими
  буквами (`examples/*.txt`):

```
# комментарий
A: B C
B: D
C:
```

```
$ ./run.sh -p A -r examples/simple.txt -t
Граф зависимостей A (максимальная глубина 3):
  [0] A -> B, C
  [1] B -> D
  [1] C -> D, E
  [2] D -> (нет)
  [2] E -> F
  [3] F -> ... (не раскрыт: достигнута максимальная глубина)

$ ./run.sh -p A -r examples/cycle.txt -t
Граф зависимостей A (максимальная глубина 3):
  [0] A -> B
  [1] B -> C, D
  [2] C -> A
  [2] D -> D
Циклическая зависимость: A -> B -> C -> A
Циклическая зависимость: D -> D

$ ./run.sh -p A -r examples/deep.txt -t -d 2
Граф зависимостей A (максимальная глубина 2):
  [0] A -> B
  [1] B -> C
  [2] C -> ... (не раскрыт: достигнута максимальная глубина)

$ ./run.sh -p A -r examples/filter.txt -t -f X
Граф зависимостей A (максимальная глубина 3):
  [0] A -> B, C
  [1] B -> D
  [1] C -> D
  [2] D -> (нет)
Исключены фильтром: XA, XB

$ ./run.sh -p A -r examples/broken.txt -t
Ошибка репозитория: строка 1: некорректное имя пакета 'c'
$ ./run.sh -p Z -r examples/simple.txt -t
Ошибка репозитория: пакет Z не найден в репозитории
```

Реальный репозиторий:

```sh
./run.sh -p Microsoft.Extensions.Logging -r https://api.nuget.org/v3/index.json -v 8.0.0 -d 3
./run.sh -p Microsoft.Extensions.Logging -r https://api.nuget.org/v3/index.json -v 8.0.0 -f Diagnostics
```

## Этап 4. Порядок загрузки

`-l` выводит порядок, в котором каждый пакет загружается после своих
зависимостей (алгоритм Кана; при равенстве — по имени). Если остались
только пакеты из цикла, цикл разрывается на пакете с наименьшим числом
незагруженных зависимостей (`(разрыв цикла)`); зависимость пакета от
самого себя загрузку не блокирует.

```
$ ./run.sh -p APP -r examples/diamond.txt -t -l
Порядок загрузки зависимостей для APP:
  1. CORE
  2. LOG
  3. DATA
  4. WEB
  5. APP

$ ./run.sh -p A -r examples/simple.txt -t -l
Порядок загрузки зависимостей для A:
  1. D
  2. B
  3. F
  4. E
  5. C
  6. A

$ ./run.sh -p A -r examples/cycle.txt -t -l
Порядок загрузки зависимостей для A:
  1. D
  2. A (разрыв цикла)
  3. C
  4. B
```

### Сравнение с NuGet

```sh
dotnet new console -o cmp && cd cmp
dotnet add package Serilog.Sinks.Console --version 6.0.0
dotnet list package --include-transitive   # итоговый набор пакетов
# граф с версиями: obj/project.assets.json, раздел "targets"

./run.sh -p Serilog.Sinks.Console -r https://api.nuget.org/v3/index.json -v 6.0.0 -d 10 -l
```

Причины возможных расхождений:

1. **Целевая платформа.** В `.nuspec` зависимости разбиты на группы по
   платформам (`net462`, `netstandard2.0`, `net8.0`…). NuGet берёт одну
   группу — подходящую к платформе проекта, `depviz` — объединение всех
   групп, поэтому может показать лишние пакеты (например, полифилы вроде
   `System.Memory`, нужные только .NET Framework / .NET Standard).
2. **Выбор версий.** Оба берут минимальную подходящую версию, но NuGet
   учитывает все требования к пакету (*nearest wins*, для «двоюродных»
   зависимостей — максимальная из нижних границ). `depviz` фиксирует
   версию при первой встрече пакета в BFS (ближайшую к корню), поэтому
   версия может оказаться ниже, чем у NuGet.
3. **Ограничения анализа.** `--max-depth` и `--filter` отсекают часть
   графа; у NuGet таких ограничений нет.
4. **Порядок.** `dotnet restore` скачивает пакеты параллельно, а в
   `project.assets.json` они перечислены по алфавиту — строгого «порядка
   загрузки» у NuGet нет. Сравнивается состав и то, что каждый пакет
   идёт после своих зависимостей.
5. **Циклы.** NuGet при цикле завершает восстановление с ошибкой
   `NU1108`; `depviz` разрывает цикл и продолжает работу.
6. Атрибуты `include`/`exclude` и `PrivateAssets` в `depviz` не
   учитываются.

## Этап 5. Визуализация (PlantUML)

`-u` выводит текст диаграммы PlantUML, сохраняет его в `.puml` и
показывает изображение:

* если установлен `plantuml` (или задана переменная `PLANTUML_JAR` с
  путём к `plantuml.jar` и есть `java`) — PNG строится локально рядом с
  `.puml` и открывается программой просмотра;
* иначе формируется ссылка на сервер `plantuml.com` (текст сжимается
  deflate и кодируется алфавитом PlantUML) и открывается в браузере.

Оформление: корень — голубой, нераскрытые из-за глубины пакеты —
пунктиром, рёбра циклов — красные, исключённые фильтром пакеты — в легенде.

```
$ ./run.sh -p A -r examples/cycle.txt -t -u
@startuml
title Зависимости A
skinparam defaultTextAlignment center
skinparam shadowing false
rectangle "A" as n0 #LightSkyBlue
rectangle "B" as n1
rectangle "C" as n2
rectangle "D" as n3
n0 -[#red,bold]-> n1
n1 -[#red,bold]-> n2
n1 --> n3
n2 -[#red,bold]-> n0
n3 -[#red,bold]-> n3
@enduml
Изображение графа: https://www.plantuml.com/plantuml/png/PP2n3e90...
```

Примеры для трёх пакетов NuGet:

```sh
R=https://api.nuget.org/v3/index.json
./run.sh -p Serilog.Sinks.Console -r $R -v 6.0.0 -d 5 -u
./run.sh -p Microsoft.Extensions.Logging -r $R -v 8.0.0 -d 3 -u
./run.sh -p Newtonsoft.Json -r $R -v 13.0.3 -d 2 -u
```

### Сравнение со штатными средствами

У NuGet нет встроенного построителя изображения графа. Штатные способы
посмотреть зависимости:

* `dotnet list package --include-transitive` — плоский список
  прямых и транзитивных пакетов проекта с итоговыми версиями;
* `dotnet nuget why <проект> <пакет>` (.NET SDK 8.0.4xx+) — цепочки, по
  которым пакет попал в проект;
* Visual Studio: *Solution Explorer → Dependencies → Packages* — дерево;
* вкладка *Dependencies* на nuget.org — прямые зависимости по группам
  платформ.

Расхождения с ними объясняются теми же причинами, что на этапе 4:
объединение групп платформ (на графе `depviz` видны пакеты всех групп —
особенно заметно у `Newtonsoft.Json`, где у старых платформ много
зависимостей, а у современных их нет), выбор версии при первой встрече,
обрезка по глубине/фильтру. Кроме того, штатные средства показывают
дерево (общий пакет повторяется в каждой ветке), а `depviz` — граф, где
каждый пакет изображён один раз.
