# depviz — визуализация графа зависимостей NuGet

Учебная практическая работа № 2 по дисциплине «Конфигурационное управление»,
вариант 3.

## Общее описание

`depviz` — CLI-приложение для анализа зависимостей пакетов .NET (NuGet).
Готовые менеджеры пакетов и библиотеки для получения зависимостей
не используются. Реализация — Python 3.10+, только стандартная библиотека.

## Параметры

| Опция | Описание |
|---|---|
| `-p`, `--package` | имя анализируемого пакета (обязательно) |
| `-r`, `--repo` | URL репозитория NuGet или путь к файлу тестового репозитория |
| `-t`, `--test-mode` | режим работы с тестовым репозиторием |
| `-v`, `--version` | версия пакета (обязательна вне тестового режима) |
| `-d`, `--max-depth` | максимальная глубина анализа (целое ≥ 1, по умолчанию 3) |
| `-f`, `--filter` | подстрока: пакеты с ней в имени не анализируются |

Проверки параметров: формат имени пакета (в тестовом режиме — только большие
латинские буквы), схема `http/https` у URL, существование файла тестового
репозитория, формат версии, целое положительное значение глубины, фильтр не
должен исключать сам анализируемый пакет. При ошибке выводится сообщение и
возвращается код 2.

## Сборка и тесты

Сборка не требуется.

```sh
./run.sh --help        # справка
./run.sh test          # тесты (unittest)
```

## Пример (этап 1)

```
$ ./run.sh -p Serilog -r https://api.nuget.org/v3/index.json -v 4.0.0 -d 2 -f Test
package=Serilog
repo=https://api.nuget.org/v3/index.json
test_mode=False
version=4.0.0
max_depth=2
filter=Test

$ ./run.sh -p Serilog -r https://x -v 1 -d 0
Ошибка параметров: argument -d/--max-depth: значение должно быть не меньше 1, получено 0
```

## Получение зависимостей (этап 2)

Используется формат пакетов .NET (NuGet) и протокол NuGet API v3 без
сторонних библиотек:

1. Если `--repo` оканчивается на `.json`, это индекс сервиса
   (`https://api.nuget.org/v3/index.json`); из него берётся адрес ресурса
   `PackageBaseAddress/3.0.0`. Иначе `--repo` считается этим адресом
   (`https://api.nuget.org/v3-flatcontainer/`).
2. `{base}/{id}/index.json` — список версий; заданная версия проверяется
   на существование (с нормализацией: `1.0` → `1.0.0`).
3. `{base}/{id}/{версия}/{id}.nuspec` — манифест пакета; из элементов
   `<dependency>` извлекаются id и диапазон версий. Если зависимости
   разбиты на группы по целевым платформам, берётся их объединение.
4. Для каждой зависимости диапазон (`1.0`, `[1.0,2.0)`, `(,1.0]`, `[1.0]`)
   разрешается в минимальную подходящую опубликованную версию — так же,
   как это делает NuGet (правило *lowest applicable version*).

```sh
./run.sh -p Serilog.Sinks.Console -r https://api.nuget.org/v3/index.json -v 6.0.0
```
Вывод: строки вида `  <зависимость> <диапазон> -> <выбранная версия>`.

## Граф зависимостей (этап 3)

* Граф строится обходом в ширину (**BFS без рекурсии**, очередь `deque`).
  Глубина корня — 0; пакеты на глубине `--max-depth` попадают в граф,
  но их зависимости не запрашиваются.
* Пакеты, имя которых содержит подстроку `--filter` (без учёта регистра),
  исключаются из анализа вместе со своими поддеревьями.
* Каждый пакет раскрывается один раз, поэтому **циклы** не приводят к
  зацикливанию; найденные циклы выводятся (итеративный DFS по обратным
  рёбрам).
* **Тестовый режим** (`-t`): вместо URL указывается файл, где пакеты
  названы большими латинскими буквами:

```
# комментарий
A: B C
B: D
C:
```

Готовые тестовые репозитории лежат в `examples/`:
`simple.txt`, `cycle.txt`, `deep.txt`, `filter.txt`, `diamond.txt`,
`broken.txt` (ошибка формата).

```
$ ./run.sh -p A -r examples/cycle.txt -t
Граф зависимостей A (максимальная глубина 3):
  [0] A -> B
  [1] B -> C, D
  [2] C -> A
  [2] D -> D
Циклическая зависимость: A -> B -> C -> A
Циклическая зависимость: D -> D

$ ./run.sh -p A -r examples/deep.txt -t -d 2
Граф зависимостей A (максимальная глубина 2):
  [0] A -> B
  [1] B -> C
  [2] C -> ... (не раскрыт: достигнута максимальная глубина)

$ ./run.sh -p A -r examples/filter.txt -t -f X
Граф зависимостей A (максимальная глубина 3):
  [0] A -> B, C
  [1] B -> D
  [1] C -> D
  [2] D -> (нет)
Исключены фильтром: XA, XB

$ ./run.sh -p A -r examples/broken.txt -t
Ошибка репозитория: строка 1: некорректное имя пакета 'c'
```

## Порядок загрузки зависимостей (этап 4)

Опция `-l`, `--load-order` выводит порядок, в котором пакеты нужно
загрузить, чтобы каждый пакет загружался после своих зависимостей
(топологическая сортировка, алгоритм Кана, без рекурсии). При равенстве
выбирается пакет с меньшим именем. Если остались только пакеты из цикла,
цикл разрывается на пакете с наименьшим числом незагруженных
зависимостей — он помечается `(разрыв цикла)`.

```
$ ./run.sh -p APP -r examples/diamond.txt -t -l
Порядок загрузки зависимостей для APP:
  1. CORE
  2. LOG
  3. DATA
  4. WEB
  5. APP

$ ./run.sh -p A -r examples/simple.txt -t -l
Порядок загрузки зависимостей для A:
  1. D
  2. B
  3. F
  4. E
  5. C
  6. A

$ ./run.sh -p A -r examples/cycle.txt -t -l
Порядок загрузки зависимостей для A:
  1. D
  2. A (разрыв цикла)
  3. C
  4. B
```

### Сравнение с реальным менеджером пакетов

Проверка через .NET SDK:

```sh
dotnet new console -o cmp && cd cmp
dotnet add package Serilog.Sinks.Console --version 6.0.0
dotnet list package --include-transitive
# полный граф с версиями: obj/project.assets.json, раздел "targets"
```

и сравнение с

```sh
./run.sh -p Serilog.Sinks.Console -r https://api.nuget.org/v3/index.json -v 6.0.0 -d 10 -l
```

Возможные расхождения и их причины:

1. **Целевая платформа.** В `.nuspec` зависимости разбиты на группы по
   платформам (`net462`, `netstandard2.0`, `net8.0`…). NuGet берёт только
   группу, подходящую к платформе проекта, а `depviz` — объединение всех
   групп, поэтому может показать лишние пакеты (например, полифилы вроде
   `System.Memory`, нужные только для .NET Framework).
2. **Выбор версий.** Оба используют минимальную подходящую версию, но
   NuGet при конфликте учитывает все требования к пакету
   (*nearest wins*, а для «двоюродных» зависимостей — максимум из нижних
   границ). `depviz` фиксирует версию при первой встрече пакета в BFS, т.е.
   ближайшую к корню, — для «двоюродных» зависимостей версия может
   оказаться ниже, чем у NuGet.
3. **Ограничения анализа.** `--max-depth` и `--filter` отсекают часть графа;
   у NuGet таких ограничений нет.
4. **Порядок.** `dotnet restore` скачивает пакеты параллельно и не
   гарантирует порядок; в `project.assets.json` пакеты перечислены по
   алфавиту. Поэтому сравнивается не буквальный порядок, а то, что
   каждый пакет идёт после своих зависимостей, и совпадение множеств.
5. **Циклы.** NuGet при цикле завершает восстановление с ошибкой
   `NU1108`; `depviz` разрывает цикл и продолжает работу.
6. Атрибуты `include`/`exclude` и `PrivateAssets` не влияют на состав
   графа в `depviz`, а NuGet их учитывает.
